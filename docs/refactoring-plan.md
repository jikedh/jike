# 即刻（Jike）项目全面重构方案
## 1. 背景与目标
当前项目是基于 Electron、React、TypeScript、React Flow、Zustand、Tailwind CSS 构建的视频工作流桌面应用，业务能力覆盖项目管理、节点式画布、AI 生成、媒体处理、本地服务管理、任务追踪、OSS 上传与本地存储等多个领域。随着功能持续增长，项目已经进入复杂度快速上升阶段，需要通过系统性重构提升长期可维护性、可扩展性与交付稳定性。
本次重构不是单纯的目录整理，而是围绕“架构分层清晰、业务边界稳定、状态流向可控、页面交互一致、类型契约明确、验证机制可持续”展开的工程化升级。
### 1.1 当前主要问题
| 问题类型 | 典型表现 | 影响 |
| --- | --- | --- |
| 架构边界不清 | 页面、组件、服务、状态、IPC 调用之间职责混杂 | 修改一个功能容易牵连多个模块 |
| Canvas 复杂度高 | 节点、边、状态、生成流程、菜单配置分散 | 新增节点成本高，容易遗漏注册点 |
| 状态管理分散 | Zustand Store 与组件本地状态边界不明确 | 数据流难追踪，调试成本高 |
| IPC 契约不够集中 | 主进程、preload、渲染进程 API 需要多处同步 | 易出现通道不一致或类型漂移 |
| 页面体验不统一 | Loading、Empty、Error、任务进度、弹窗交互各自实现 | 用户体验不稳定，复用困难 |
| 类型与模型抽象不足 | 业务对象、节点元信息、AI 模型能力缺少统一建模 | 后续扩展依赖大量条件判断 |
| 质量门禁不足 | 缺少分层验证、重构回归清单与风险控制机制 | 大规模重构容易引入隐性问题 |
### 1.2 重构目标
1. 建立清晰的 Electron 主进程、preload、渲染进程、shared、service 分层边界。
2. 统一 Canvas 节点开发、注册、菜单、能力矩阵与持久化流程。
3. 提升页面交互一致性，沉淀通用的加载、错误、空态、任务进度和媒体预览模式。
4. 降低主流程页面和复杂组件的单文件复杂度。
5. 建立可持续的质量保障机制，让后续新增功能有明确规范和检查清单。
6. 在不改变核心业务行为的前提下，分阶段、小步、可回滚地完成重构。

## 2. 技术栈选型与升级建议
### 2.1 当前技术栈保留建议
| 技术 | 当前定位 | 建议 |
| --- | --- | --- |
| Electron 39 | 桌面运行容器 | 保留，短期不做大版本迁移 |
| electron-vite 5 | Electron 构建工具 | 保留，继续作为主构建入口 |
| React 19 | 渲染进程 UI 框架 | 保留，围绕性能和组件边界优化 |
| TypeScript 5.9 | 类型系统 | 保留，加强 shared 类型契约建设 |
| Zustand 5 | 状态管理 | 保留，但需要规范 Store 分层和 selector 使用 |
| @xyflow/react 12 | Canvas 工作流引擎 | 保留，重点优化 nodeTypes、edgeTypes、回调与节点渲染 |
| Tailwind CSS 4 | 样式系统 | 保留，统一主题变量和组件样式模式 |
| Biome 2.1 | 格式化与检查 | 保留，作为基础代码规范工具 |
| Radix UI | 无头组件基础 | 保留，适合统一弹窗、菜单、Popover、Tooltip 等交互 |
### 2.2 升级策略
不建议在重构第一阶段同步进行大量依赖升级。重构与升级应拆分为两个阶段，避免问题来源混杂。
#### 阶段一：稳定重构期
- 保持 Electron、React、Vite、TypeScript 主版本不变。
- 仅允许修复安全漏洞或明确兼容的小版本升级。
- 优先完成目录、分层、状态、IPC、Canvas 节点体系的结构性改造。
#### 阶段二：技术升级期
- 升级前先建立依赖影响清单。
- 优先升级低风险工具链依赖，例如 Biome、类型包、非运行时工具。
- 再升级运行时相关依赖，例如 Electron、Vite、React Flow。
- 每次升级只处理一组相关依赖，避免一次性大范围变更。
### 2.3 建议补充的工程能力
| 能力 | 建议方案 | 价值 |
| --- | --- | --- |
| 类型契约集中管理 | 在 `src/shared/types/` 中统一定义 IPC、Canvas、Project、Asset、AI Task 类型 | 降低跨进程类型漂移 |
| 节点能力矩阵 | 在 `src/shared/constants/` 或 Canvas 专属配置中维护模型能力 | 减少组件内部复杂条件判断 |
| API 服务边界 | 渲染进程统一通过 `src/renderer/services/` 调用业务服务 | 降低页面直接依赖底层实现 |
| 错误模型 | 定义统一错误结构，如业务错误、网络错误、IPC 错误、本地资源错误 | 提升错误展示与排查效率 |
| 文档化开发清单 | 为新增节点、IPC、页面模块提供固定步骤 | 降低多人协作成本 |

## 3. 页面交互体验优化策略
### 3.1 统一页面状态模型
建议所有页面统一采用以下状态模型：
```ts
type PageStatus = 'idle' | 'loading' | 'success' | 'empty' | 'error'
```
页面不应各自实现分散的 Loading、Empty、Error。建议抽象为通用页面状态组件，例如：
- `PageLoading`
- `PageEmpty`
- `PageError`
- `TaskProgress`
- `MediaPreviewFallback`
适用页面包括：Home、Canvas、Video、Assets、Voice、Settings、Points、Login 等。
### 3.2 Canvas 交互优化
Canvas 是项目维护成本最高的区域，应重点优化。
#### 3.2.1 节点创建体验
- 统一节点搜索、节点菜单、节点分组和节点元信息。
- 节点配置以数据驱动方式维护，避免菜单、类型、组件、默认数据分散定义。
- 新增节点必须包含：节点类型 ID、显示名称、分组、图标、输入能力、输出能力、默认数据、组件映射。
#### 3.2.2 节点运行体验
- 节点执行状态统一为 `idle`、`pending`、`running`、`success`、`failed`、`cancelled`。
- 节点卡片统一展示任务状态、错误原因、重试入口、输出预览。
- AI 生成任务、视频处理任务、上传任务应复用同一套任务状态 UI。
#### 3.2.3 性能体验
- `nodeTypes`、`edgeTypes`、`defaultEdgeOptions`、上下文菜单配置必须保持稳定引用。
- 节点组件使用 `memo`，避免订阅过大的 Store state。
- 高频拖拽、缩放、连线事件中避免创建临时对象和触发全局状态更新。
- 媒体资源优先展示缩略图或压缩预览，不在画布中直接加载原图或大视频。
### 3.3 弹窗与表单交互统一
建议基于 Radix UI 与现有 `src/renderer/components/ui/` 组件统一以下模式：
| 场景 | 优化策略 |
| --- | --- |
| 项目创建/编辑 | 使用统一 Dialog 表单布局，固定标题、描述、按钮区 |
| 删除/覆盖确认 | 使用统一 Confirm Dialog，明确风险与不可逆操作 |
| 参数设置 | 使用分组表单，区分基础参数、高级参数、模型能力参数 |
| 长任务反馈 | 使用非阻塞进度提示，允许用户继续操作其他区域 |
| 错误提示 | 错误信息分为用户可读描述和开发调试详情 |
### 3.4 媒体预览体验
- 图片、视频、音频、全景资源采用统一预览容器。
- 预览组件只负责展示，不负责上传、下载、任务轮询等业务逻辑。
- 加载失败时显示统一 fallback，提供重新加载或定位本地文件入口。
- 大资源预览必须限制尺寸，避免撑开布局或导致 Canvas 卡顿。

## 4. 代码分层架构设计方案
### 4.1 目标架构分层
建议重构后采用以下分层：
```text
src/
├── main/                    # Electron 主进程：窗口、IPC、原生能力、本地服务
├── preload/                 # Context Bridge：白名单 API 暴露，不写业务逻辑
├── renderer/                # React 渲染进程：页面、组件、hooks、stores、services
├── service/                 # 跨进程可复用业务服务
└── shared/                  # 类型、常量、纯工具、跨进程契约
```
### 4.2 主进程分层
主进程建议按领域组织，不在入口文件堆叠业务逻辑。
```text
src/main/
├── index.ts                 # 只负责应用生命周期、窗口创建、IPC 注册、更新器启动
├── ipc/
│   ├── index.ts             # IPC 注册中心
│   ├── storage/             # 本地项目和媒体存储
│   ├── download/            # 下载能力
│   ├── video-processing/    # 视频裁剪处理
│   ├── adobe2api/           # 本地 Python 服务管理
│   ├── tracking/            # 任务追踪上报
│   └── debug/               # 调试能力
├── modules/                 # 数据库、服务管理、IPC 管理等基础模块
└── utils/                   # 主进程专用工具
```
主进程原则：
1. `index.ts` 不直接实现业务细节。
2. IPC 处理器只负责参数接收、边界校验、调用服务、返回结果。
3. 文件系统、数据库、外部进程、本地服务启动停止必须留在主进程。
4. 不在主进程依赖渲染进程代码。
### 4.3 Preload 分层
Preload 是安全边界，只做 API 白名单暴露。
```text
src/preload/
├── index.ts                 # contextBridge 暴露 API
└── index.d.ts               # window API 类型声明
```
Preload 原则：
1. 禁止直接暴露 `ipcRenderer` 或 Electron 原始对象。
2. 禁止在 preload 中写业务逻辑。
3. 每个暴露 API 对应一个明确 IPC 通道。
4. `index.d.ts` 与 `index.ts` 必须同步维护。
### 4.4 渲染进程分层
建议将渲染进程拆成页面层、业务服务层、状态层、组件层、工具层。
```text
src/renderer/
├── pages/                   # 页面级模块
│   ├── Home/
│   ├── Canvas/
│   ├── Video/
│   ├── Assets/
│   └── Settings/
├── components/              # 跨页面通用组件
│   ├── ui/                  # 基础 UI 组件
│   ├── media/               # 媒体预览组件
│   ├── task/                # 任务状态组件
│   └── layout/              # 页面布局组件
├── hooks/                   # 通用 Hooks
├── services/                # 渲染进程业务服务与 IPC 封装
├── stores/                  # Zustand Store
└── utils/                   # 渲染进程工具
```
### 4.5 Canvas 模块目标结构
Canvas 建议作为重点模块独立治理。
```text
src/renderer/pages/Canvas/
├── index.tsx                # 页面入口，只组合核心模块
├── canvas-config.ts         # React Flow 静态配置
├── canvas-actions.ts        # 页面级动作编排
├── CustomNodes/             # 节点组件
├── CustomEdge/              # 连线组件
├── components/              # Canvas 内部组件
├── hooks/                   # Canvas 专用 Hooks
├── services/                # Canvas 业务服务
├── stores/                  # Canvas 专用状态切片或选择器
└── types.ts                 # Canvas 局部类型
```
Canvas 原则：
1. 页面入口只负责组合，不承载复杂业务逻辑。
2. 节点组件只负责展示与局部交互，不直接处理复杂任务编排。
3. 节点注册、菜单配置、默认数据、能力矩阵尽量配置化。
4. 任务执行、轮询、持久化、上传下载放入 service 或 hook。
5. Store selector 要细粒度，避免节点组件订阅整个 Store。
### 4.6 Shared 类型与常量设计
建议在 `src/shared/` 下形成稳定契约：
```text
src/shared/
├── constants/
│   ├── ai-models.ts
│   ├── node-capabilities.ts
│   ├── task-status.ts
│   └── ipc-channels.ts
├── types/
│   ├── canvas.ts
│   ├── project.ts
│   ├── asset.ts
│   ├── task.ts
│   ├── ipc.ts
│   └── api.ts
└── utils/
```
重点建议：
- IPC 通道名称集中定义，减少字符串散落。
- AI 模型能力集中定义，页面根据能力渲染参数和禁用态。
- 任务状态、节点状态、资源类型使用统一枚举或常量。
- shared 中只放纯类型、纯常量、纯工具，不依赖 Electron 或 React。

## 5. 重构实施步骤规划
### 5.1 总体原则
1. 小步提交，小步验证，避免一次性大改。
2. 先定边界，再迁移代码，最后优化体验。
3. 优先重构高变更、高耦合、高复用区域。
4. 每个阶段都要保证主流程可用。
5. 不在同一阶段同时做架构重构和大版本依赖升级。
### 5.2 阶段一：现状盘点与边界定义
#### 目标
明确项目模块、依赖关系、高风险文件和重构优先级。
#### 具体任务
1. 梳理页面清单：Home、Canvas、Video、Assets、Voice、Settings、Points、Login。
2. 梳理主进程 IPC 通道清单：storage、download、debug、video-processing、adobe2api、tracking。
3. 梳理 Zustand Store 清单及其被哪些页面使用。
4. 梳理 Canvas 节点类型、节点组件、菜单入口、默认数据和持久化字段。
5. 标记高复杂文件：超过 500 行、职责超过 3 类、包含大量条件判断的文件优先治理。
6. 输出模块依赖图和重构优先级列表。
#### 交付物
- 模块清单
- IPC 通道清单
- Store 使用清单
- Canvas 节点清单
- 高风险文件清单
### 5.3 阶段二：类型契约与常量集中
#### 目标
先稳定跨模块契约，为后续迁移提供基础。
#### 具体任务
1. 建立统一任务状态类型。
2. 建立统一资源类型，例如 image、video、audio、text、panorama。
3. 建立 Canvas 节点基础类型，包括节点 ID、节点类型、输入输出、运行状态、错误信息。
4. 建立 IPC 通道常量，替换散落字符串。
5. 建立 AI 模型能力矩阵，用配置替代组件内复杂判断。
6. 将只读常量移动到 `src/shared/constants/`。
#### 交付物
- `shared/types/task.ts`
- `shared/types/canvas.ts`
- `shared/types/ipc.ts`
- `shared/constants/ipc-channels.ts`
- `shared/constants/node-capabilities.ts`
### 5.4 阶段三：IPC 与 Preload 治理
#### 目标
保证主进程、preload、渲染进程之间的调用路径清晰可控。
#### 具体任务
1. 按领域检查 IPC 注册是否集中在 `src/main/ipc/index.ts`。
2. 为每个 IPC 模块明确输入、输出、错误结构。
3. 将渲染进程直接调用 `window.xxx` 的逻辑封装到 `src/renderer/services/`。
4. 同步更新 `src/preload/index.ts` 与 `src/preload/index.d.ts`。
5. 对文件系统、下载、视频处理、本地服务操作增加边界校验。
#### 交付物
- IPC 通道注册规范
- preload API 类型声明
- renderer service 封装层
- IPC 错误处理约定
### 5.5 阶段四：Canvas 模块重构
#### 目标
降低 Canvas 新增节点、维护节点、调试节点的成本。
#### 具体任务
1. 抽离 `nodeTypes`、`edgeTypes`、默认边配置，保证稳定引用。
2. 建立节点元信息配置表，统一节点名称、类型、分组、图标、默认数据。
3. 将节点菜单、节点搜索、节点创建逻辑改为读取统一配置。
4. 节点组件统一使用 `memo`。
5. 将节点任务执行逻辑移出组件，放入 hook 或 service。
6. 将媒体预览、任务状态、错误展示组件化。
7. Store selector 细粒度改造，避免节点组件订阅整棵状态树。
8. 针对高频交互回调使用稳定函数引用。
#### 交付物
- Canvas 配置化节点体系
- 节点组件重构清单
- Canvas Store selector 规范
- 节点任务状态 UI
### 5.6 阶段五：页面与组件体系治理
#### 目标
提升页面体验一致性与组件复用能力。
#### 具体任务
1. 抽象页面布局组件，例如页面标题区、内容区、操作区。
2. 抽象页面状态组件：Loading、Empty、Error。
3. 抽象媒体展示组件：图片、视频、音频、全景预览。
4. 抽象任务反馈组件：任务进度、失败重试、生成结果。
5. 统一 Dialog、Confirm、Popover、Tooltip 的使用方式。
6. 清理页面中的重复样式和重复交互逻辑。
#### 交付物
- 页面状态组件
- 媒体预览组件
- 任务反馈组件
- 页面布局组件
- 通用弹窗模式
### 5.7 阶段六：状态管理治理
#### 目标
让状态来源、更新路径、订阅范围更加清晰。
#### 具体任务
1. 区分全局状态、页面状态、组件局部状态、服务端/任务状态。
2. Store 中只保留需要跨组件共享的状态。
3. 将派生数据优先放在 selector 或 memo 中，不重复存储。
4. Store action 命名统一，使用业务动词表达意图。
5. 避免组件直接组合复杂 Store 更新逻辑，复杂流程移入 service 或 action。
6. 清理长期不用的状态字段。
#### 交付物
- Store 分层规范
- Store action 命名规范
- Canvas Store 拆分或 selector 优化结果
- 状态字段清理清单
### 5.8 阶段七：体验优化与性能优化
#### 目标
在架构稳定后，再集中处理体验和性能问题。
#### 具体任务
1. 优化 Canvas 大量节点情况下的渲染性能。
2. 优化媒体资源加载策略，增加缩略图和懒加载策略。
3. 优化任务进度反馈，避免用户误以为应用卡死。
4. 优化页面切换和长任务场景下的交互阻塞。
5. 针对大组件使用 React DevTools 或手动日志定位重复渲染来源。
#### 交付物
- Canvas 性能优化清单
- 媒体加载策略
- 任务交互优化方案
- 关键页面体验优化结果
### 5.9 阶段八：质量保障与文档固化
#### 目标
将重构成果变成长期规范。
#### 具体任务
1. 编写新增 IPC 通道流程文档。

## 6. 风险评估与应对措施
| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 重构范围过大导致主流程不可用 | 高 | 按阶段推进，每阶段只处理一类问题 |
| Canvas 改造引入节点行为变化 | 高 | 先建立节点清单和字段映射，再逐个迁移 |
| IPC 通道调整造成渲染进程调用失败 | 高 | 先集中通道常量，再替换调用点 |
| Store 拆分导致状态丢失 | 中高 | 先补充状态字段清单，迁移前后保持字段兼容 |
| 类型收敛引发大量编译问题 | 中 | 从 shared 基础类型开始，逐步替换，不一次性全量强约束 |
| 依赖升级引入兼容问题 | 中 | 依赖升级放到架构重构之后单独进行 |
| 视觉统一影响已有使用习惯 | 中 | 保持核心交互路径不变，只统一反馈和组件样式 |
| 长任务改造影响本地服务生命周期 | 高 | Adobe2API、视频处理、任务追踪单独设为高风险模块 |
| 资源路径处理错误 | 高 | 主进程统一使用 `path.join`，避免硬编码分隔符 |

## 7. 重构后的质量保障机制
### 7.1 分层质量门禁
| 层级 | 检查重点 |
| --- | --- |
| main | IPC 是否按领域注册，是否包含边界校验，是否避免业务堆叠到入口文件 |
| preload | 是否只暴露白名单 API，是否同步类型声明，是否没有业务逻辑 |
| renderer pages | 页面是否只负责编排，复杂逻辑是否下沉到 hook/service |
| components | 是否单一职责，是否可复用，是否避免业务耦合 |
| stores | 是否只保存共享状态，selector 是否细粒度，action 是否语义清晰 |
| shared | 是否只包含纯类型、常量、工具，不依赖 React 或 Electron |
### 7.2 Canvas 节点质量清单
新增或修改 Canvas 节点时必须检查：
1. 是否有唯一节点类型 ID。
2. 是否已加入节点元信息配置。
3. 是否已注册节点组件。
4. 是否已配置菜单分组和搜索关键词。
5. 是否定义默认数据结构。
6. 是否明确输入、输出资源类型。
7. 是否使用统一任务状态。
8. 是否使用统一错误展示。
9. 是否避免在节点组件内写复杂任务编排。
10. 是否避免订阅整个 Canvas Store。
### 7.3 IPC 质量清单
新增或修改 IPC 通道时必须检查：
1. 主进程是否有对应 `ipcMain.handle`。
2. IPC 注册中心是否已注册。
3. Preload 是否暴露白名单 API。
4. `index.d.ts` 是否同步声明。
5. 渲染进程是否通过 service 调用，而不是到处直接访问 `window.xxx`。
6. 是否有参数校验和错误返回结构。
7. 是否没有暴露 Electron 原始对象。
### 7.4 代码评审清单
重构后代码评审建议重点关注：
- 是否引入新的跨层依赖。
- 是否出现重复业务逻辑。
- 是否新增大文件或大组件。
- 是否把服务逻辑写入 UI 组件。
- 是否把 UI 状态写入全局 Store。
- 是否出现大量条件判断，是否可以配置化。
- 是否存在不稳定引用导致 React Flow 重渲染。
- 是否有路径分隔符硬编码。
### 7.5 手动验收建议
每个阶段完成后建议人工检查以下主流程：
1. 启动应用并进入项目列表。
2. 创建项目并进入 Canvas。
3. 新增、移动、连接、删除节点。
4. 保存并重新打开项目。
5. 执行一次 AI 生成类任务。
6. 预览图片、视频、音频资源。
7. 执行视频处理或本地服务相关能力。
8. 检查任务追踪与错误提示是否正常。
9. 打包前检查主进程资源路径与本地服务路径。

## 8. 可维护性提升目标
### 8.1 结构目标
| 指标 | 目标 |
| --- | --- |
| 页面入口复杂度 | 页面入口只做组合和流程编排，避免承载大量业务逻辑 |
| 单组件职责 | 一个组件只负责一个明确展示或交互职责 |
| IPC 一致性 | 每个 IPC 通道在主进程、preload、类型声明、renderer service 中可追踪 |
| Canvas 节点开发 | 新增节点从“多处找注册点”变成“按配置和清单补齐” |
| shared 契约 | 跨进程共享类型和常量集中管理，减少重复定义 |
### 8.2 开发效率目标
| 场景 | 重构前 | 重构后目标 |
| --- | --- | --- |
| 新增 Canvas 节点 | 需要理解多个分散文件 | 按节点开发清单完成 |
| 新增 IPC 通道 | 容易遗漏 preload 或类型声明 | 按固定四步流程完成 |
| 修改页面状态 | 每个页面单独处理 | 复用统一页面状态组件 |
| 修改任务状态展示 | 多处重复修改 | 修改统一任务组件 |
| 定位状态问题 | 需要追踪多个组件和 Store | 通过 Store action 与 selector 定位 |
### 8.3 质量目标
1. 减少重复代码和重复交互实现。
2. 降低大组件和大文件数量。
3. 降低跨层直接依赖。
4. 减少 Canvas 节点新增和修改时的遗漏点。
5. 提升任务状态、错误提示、资源预览的一致性。
6. 提升复杂页面性能稳定性，降低无效重渲染。
7. 让后续功能开发可以遵循固定模板和检查清单。

## 10. 建议落地顺序
建议按以下顺序启动重构：
1. 先冻结大范围功能新增，只允许关键 bug 修复。
2. 完成模块、IPC、Store、Canvas 节点现状盘点。
3. 建立 shared 类型、任务状态、IPC 通道常量。
4. 治理 preload 与 renderer service 调用边界。
5. 重构 Canvas 节点配置体系和节点任务状态 UI。
6. 统一页面状态、媒体预览、任务反馈组件。
7. 优化 Canvas 性能与资源加载。
8. 固化开发文档、检查清单和评审标准。
9. 最后再进入依赖升级和构建流程优化。
---
## 11. 结论
本项目的重构重点不应是一次性重写，而应是通过分层、配置化、类型契约、统一交互和质量清单逐步降低复杂度。优先治理 Canvas、IPC、状态管理和任务反馈这四个高复杂区域，可以最快提升维护效率并降低后续功能开发风险。
重构完成后，项目应达到以下状态：
- 新增业务能力有清晰入口和模板。
- 跨进程 API 有统一契约。
- Canvas 节点体系可配置、可扩展、可检查。
- 页面体验一致，错误与任务反馈可复用。
- 状态流向清晰，复杂逻辑不再堆叠在组件中。
- 后续代码评审能够依据清单判断质量，而不是依赖个人经验。
